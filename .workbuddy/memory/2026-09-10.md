## 第二轮：P0 缺陷修复（当日 18:59 起）

### 最重要发现：掩模泄漏根因不在分割，而在「神经掩模无条件覆盖」

**三步递进定位（每步以实测排除假设，值得复用）：**

1. 写 `tests/diagnose_mask_quality.py`（masks_16k 作 golden baseline）→ 发现**规则引擎在 LR 下正常**
   （印章 0.0119%、IoU 0.700），泄漏不在分割阶段。
2. 检验产物层 alpha 分布 → **硬二值双峰**（>200 占 18.79%，中间灰度仅 0.19%），与源图亮度相关性 ≈0
   → 排除引导滤波连续泄漏。
3. 直接跑 `GroundedSAMProvider` → 神经输出填充率与产物**精确吻合**（印章 8.7745% vs 8.775%）→ 锁定根因。

**根因**：`grounded_sam_provider.segment_objects` 中 `final_masks[k] = m` **无条件覆盖**规则掩模。
Grounding DINO 在**金地背景**上对 `"red stamp . cinnabar seal"` 产生假阳性大框
（box_threshold=0.25 过低、单框面积上限 30% 过松），SAM2 抠出大片金地。
另有一条：ROI 检测 `|profile - median(profile)| > 5.0` 在本图（外框灰度 88 / 画心 183 / 行中位数 160）
失效，导致 ROI=整幅画、`~roi_mask` 恒空 → 外框层变空层。

**修复**（commit 3281893）：
- `grounded_sam_provider` 新增**神经掩模质量门**：面积预算（按语义类别）+ 相对放大倍数(>3x) + IoU 三重校验；
  未通过者保留规则掩模并告警。box_threshold 0.25→0.35、单框面积上限 30%→8%。
- `segmentation_provider` 新增 `_detect_painting_roi`：边缘带/中心区双参考 + 连续 run 判定。

**效果**：印章 8.7745%→0.0119%（IoU 0.700）、芦雁 6.6332%→0.1744%、题跋 2.7458%→0.2475%、
人物 6.6537%→0.2683%（基线 0.2346%）、外框 0.0762%→24.9432%（空层修复）、折痕 IoU 0.079→0.706。
**结构性缺陷 6 层 → 0 层。**

### 本轮新增的复用性发现（重要）

1. **`06_verify_psb.py` 的 MAE 对掩模不敏感**：修复前后两版产物 MAE 均为 3.498、
   均值 RGB 完全相同 —— 因为 Section 5 都是同一个 RealESRGAN 超分结果。
   该指标只能反映超分链路差异。**掩模正确性必须用相对 baseline 的 IoU/面积判定**。
2. **R6 的正确检验方式**：「图层叠加结果 vs Section 5」，而非「Section 5 vs 源图」。
3. **区域层 vs 元素层判定分离**：远山/折痕/外框/水波这类层语义边界本就主观，
   面积失衡应降级为 DRIFT 提示；否则审计会因"远山该多大"的分歧长期 FAIL 而失去信号价值。
4. **torch 不可用 RTX 5070**：`sm_120 is not compatible`（torch 2.6.0+cu124 仅到 sm_90），
   GroundingDINO/SAM2 实际 CPU 推理，Step 1 耗时 102.68s（占总 35%）。
5. **Step 4 熔断真实触发**：LaMa 批量张量尺寸不匹配（`[2,3,486,512]` vs `[?,3,512,512]`）
   回落 Telea。熔断工作正常，但批处理尺寸未对齐是真实缺陷。

**3. LaMa —— ⚠️ 修复前部分失效，已修复**

`_inpaint_tiled` 切片起算 `range(0, max(1, h-512), 448)` 在 ROI 任一维度 <512 时返回 [0]，
`[0:512]` 被 Python 截断产生非 512 tile →
① batch stack 与 OpenVINO 固定输入 `[?,3,512,512]` 不符 → 整批熔断回退 Telea；
② 回退后回填 `(396,512,3) * hann(512,512,1)` **广播失败抛 ValueError**
（生产中由 deocclusion_operator 外层 try/except 兜底成 Telea，所以没暴露）。

| ROI | 修复前 | 修复后 |
|---|---|---|
| 396×696 | 熔断+异常 0.61s（Telea） | **无熔断 4.58s（LaMa）** |
| 696×396 | 熔断+异常 0.45s | **无熔断 2.07s** |
| 696×696 / 796×796 / 996×1196 | 正常 | 正常 |

修复：新增 `_tile_starts()` 保证切片完整 + `_pad_to_tile()` 统一补齐到 512，
以 th/tw 实际尺寸记账并同步裁剪 hann 窗。commit `9e3507e`。

**探针踩坑记录**：首版 probe_lama 用**圆形小洞（900px）**，触发 `inpaint()` 第 116 行的

### 第四轮：硬件配置实效实测（用户提问驱动）

**设备清单**：CPU (Ultra 9 285H) / GPU.0 (Arc 140T 16GB iGPU) / GPU.1 (RTX 5070 Laptop 8GB dGPU) / NPU (AI Boost)

**LaMa ONNX 跨设备实测（512×512，scratch/probe_hardware.py）**：

| 设备 | 编译 | 推理 |
|---|---|---|
| CPU | 12.24s | 1.072s |
| **GPU.0 (Arc)** | 22.19s | **0.223s ← 最快** |
| GPU.1 (5070) | 21.26s | 1.222s |
| NPU | — | ❌ 编译失败（动态 shape） |

⇒ **Arc 140T 在 OpenVINO 路径下比 RTX 5070 快 5.5 倍**（OpenVINO 对 NVIDIA 走 OpenCL、
对 Intel 走原生 Level Zero）。**"5070 主算力 + Arc 仅护盾"的架构假设在本技术栈下相反。**

**PyTorch 决定性测试**：
```
torch 2.6.0+cu124  编译架构仅到 sm_90；5070 = sm_120
cuda.is_available() = True（有误导性）
2048x2048 矩阵乘 → RuntimeError: no kernel image is available
```
⇒ **5070 无法被 PyTorch 使用**，所以 `grounded_sam_provider` 里 `device="cpu"` 是版本限制下的必然，
不是代码偷懒。PyPI 上 torch 2.7.0~2.14.0 已可用（支持 Blackwell）。

**实际分工 vs 文档定位**：
| 硬件 | 文档定位 | 实际 |
|---|---|---|
| 5070 | 主算力 | 仅 LaMa；且比 Arc 慢 5.5x |
| Arc 140T | 护盾 | **实际主力**（RealESRGAN 全图超分，主动从 5070 切换） |
| NPU | UI 可选项 | **零使用**（grep 仅命中配置文件） |
| CPU | 熔断兜底 | **扛下最重的 Step1** 分割 102.68s（占端到端 35%） |

**改进路径**：A 升级 torch≥2.7+cu128 让分割上 GPU（收益最大）｜B 分割模型转 OpenVINO IR｜
C 设备策略改实测选优（LaMa 默认 GPU.1 → GPU.0，5.5x）｜D 为 NPU 选适配模型（优先级最低）

**教训**：profile_config 的性能假设与实测相反，继续沿用会把最重的算子派给最慢的设备。
