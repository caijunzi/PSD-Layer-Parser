## 第二轮：P0 缺陷修复（当日 18:59 起）

### 最重要发现：掩模泄漏根因不在分割，而在「神经掩模无条件覆盖」

**三步递进定位（每步以实测排除假设，值得复用）：**

1. 写 `tests/diagnose_mask_quality.py`（masks_16k 作 golden baseline）→ 发现**规则引擎在 LR 下正常**
   （印章 0.0119%、IoU 0.700），泄漏不在分割阶段。
2. 检验产物层 alpha 分布 → **硬二值双峰**（>200 占 18.79%，中间灰度仅 0.19%），与源图亮度相关性 ≈0
   → 排除引导滤波连续泄漏。
3. 直接跑 `GroundedSAMProvider` → 神经输出填充率与产物**精确吻合**（印章 8.7745% vs 8.775%）→ 锁定根因。

**根因**：`grounded_sam_provider.segment_objects` 中 `final_masks[k] = m` **无条件覆盖**规则掩模。
Grounding DINO 在**金地背景**上对 `"red stamp . cinnabar seal"` 产生假阳性大框
（box_threshold=0.25 过低、单框面积上限 30% 过松），SAM2 抠出大片金地。
另有一条：ROI 检测 `|profile - median(profile)| > 5.0` 在本图（外框灰度 88 / 画心 183 / 行中位数 160）
失效，导致 ROI=整幅画、`~roi_mask` 恒空 → 外框层变空层。

**修复**（commit 3281893）：
- `grounded_sam_provider` 新增**神经掩模质量门**：面积预算（按语义类别）+ 相对放大倍数(>3x) + IoU 三重校验；
  未通过者保留规则掩模并告警。box_threshold 0.25→0.35、单框面积上限 30%→8%。
- `segmentation_provider` 新增 `_detect_painting_roi`：边缘带/中心区双参考 + 连续 run 判定。

**效果**：印章 8.7745%→0.0119%（IoU 0.700）、芦雁 6.6332%→0.1744%、题跋 2.7458%→0.2475%、
人物 6.6537%→0.2683%（基线 0.2346%）、外框 0.0762%→24.9432%（空层修复）、折痕 IoU 0.079→0.706。
**结构性缺陷 6 层 → 0 层。**

### 本轮新增的复用性发现（重要）

1. **`06_verify_psb.py` 的 MAE 对掩模不敏感**：修复前后两版产物 MAE 均为 3.498、
   均值 RGB 完全相同 —— 因为 Section 5 都是同一个 RealESRGAN 超分结果。
   该指标只能反映超分链路差异。**掩模正确性必须用相对 baseline 的 IoU/面积判定**。
2. **R6 的正确检验方式**：「图层叠加结果 vs Section 5」，而非「Section 5 vs 源图」。
3. **区域层 vs 元素层判定分离**：远山/折痕/外框/水波这类层语义边界本就主观，
   面积失衡应降级为 DRIFT 提示；否则审计会因"远山该多大"的分歧长期 FAIL 而失去信号价值。
4. **torch 不可用 RTX 5070**：`sm_120 is not compatible`（torch 2.6.0+cu124 仅到 sm_90），
   GroundingDINO/SAM2 实际 CPU 推理，Step 1 耗时 102.68s（占总 35%）。
5. **Step 4 熔断真实触发**：LaMa 批量张量尺寸不匹配（`[2,3,486,512]` vs `[?,3,512,512]`）
   回落 Telea。熔断工作正常，但批处理尺寸未对齐是真实缺陷。

### 第五轮：技术栈适配性专业评估（用户提供硬件截图后）

产出 `docs/技术栈适配性专业评估与建议_20260910.md`。

**有效分辨率核算（重要纠正）**：本次 16K 产物输入是 `source_4000.jpg`（4000×1952，7.81MP），
非文档 §1.2 的壁布循环单元（388×718）。故：
- 有效源分辨率 = 4000px / 106.67in = **37.5 PPI**（不是 11 PPI）
- 放大倍率 **4.0×**（不是 13.7×）
- 频域约束：源图真实带宽 ≤2000 cycles/width，产物宣称 8000 → **约 75% 频率内容是生成的**
- 两条业务线的分辨率数据**不可混用**（壁布线 vs 16K 母版线）

**核心判断（三处结构性错配）**：

1. 🔴 **开放词汇大模型做封闭 5 类**：GroundingDINO 的价值是"任意 prompt 的开放词汇检测"，
   但项目 ADR-012 明确只需固定 5 类 → 用不上的能力换来 850MB 模型 + 102s CPU 推理 +
   金地假阳性（就是 605 倍泄漏的元凶）+ 2.9GB third_party 依赖。
   正解：5 类图上微调轻量分割器（U-Net/SegFormer-B0，10~50MB），可跑 NPU，预计 102s→数秒。
2. 🔴 **生成式超分做印前交付**：RealESRGAN 高频 28.16×、往返 MAE 4.782（Lanczos 1.110），
   即**改变像素、无法还原源图**。违反铁律 R1；且 Step5 生成像素近 100% 却零标记，
   而 Step4 仅 0.31% 却做了标记——**标记策略与生成规模倒挂**。
   也解释了 MAE 为何无法≤2.0：**"MAE≤2.0"与"用生成式超分"数学上互斥**。
3. 🔴 **PLATE 线未打通**：五算子实现但未接入，产物为 RGB；算力全服务 DESIGN 线，
   真正付费的印前能力（CMYK/专色/陷印/微孔）一个未产出。

**硬件结论**：硬件没买错（AI PC 合理配置），但调度错配——
Arc 实测最快却只当"护盾"、5070 因 torch sm_120 完全闲置、NPU 零调用、CPU 扛最重的分割。
8GB 显存跑不了 20B 级模型，但**本项目不需要大模型**（ADR-010 自己写了不引入扩散模型）。

**三条路线**：A 收敛为严肃印前工具（打通 PLATE + 诚实超分 + 专用小模型，端到端 294s→60~90s）
｜B 强化为设计师辅助（放弃印前严肃性）｜C 混合（DESIGN 可生成 / PLATE 禁生成，即 ADR-011 本意）

### 第八轮：PLATE 产出真 CMYK + 修复内核编译器（commit 2a76ad2）

**🔴 重大发现：`engine/core/psd_compiler.py` 从未被真正执行过。**
生产一直走 `engine/psb_builder.py`，所以内核的错误从未暴露。首次真跑即报：
```
ValueError: Color '0' is not valid for color mode '4', expected '0'
```
根因：图层通道用**整数索引** 0/1/2(/3)，而 pytoshop 的 `ColorChannelMapping`
把整数 0 解释为 `ColorChannel.bitmap` → 与 RGB/CMYK 模式都不匹配。

实测三种写法，只有一个正确（重要，勿再踩）：
| 写法 | 结果 |
|---|---|
| `set_channel(0, ...)` | ❌ bitmap 冲突 |
| `Image(channels={ColorChannel.cyan: ...})` | ❌ 字典键要求 `ChannelId`，不是 `ColorChannel` |
| **`set_channel(ColorChannel.cyan, ...)` + Image 显式传 `color_mode`** | ✅ 唯一正确 |

⇒ `_cmyk_channels`/`_rgba_channels` 合并为 `_apply_cmyk`/`_apply_rgba`。
⇒ 修正后内核**真正可用**（RGB/CMYK 双线 5 项测试全绿），为后续内核合流（G1/G2）扫清障碍。

**psb_builder 增加 CMYK**：
- `color_mode` 参数（rgb/cmyk）+ `_apply_layer_channels()` 统一落通道
- ⚠️ **反码约定差异**：`ColorManager.bgr_to_cmyk_raw` 输出**已是 PSD 磁盘反码**（255=0%墨），
  直接给 pytoshop，**不得再 `255-x` 二次反转**；而 `core/psd_compiler` 内部用逻辑墨量、
  在 `_to_disk()` 统一反转。两条路径约定不同，混用会双重反转。
- 新增 `last_tac` 记录 TAC 实测值

**端到端实测（--mode plate，226.1s）**：
- 产物 `color_mode=4 (CMYK)`、`channels=4`、16000×7808、11 图层、**1.40 GB**
- 每层 5 通道（CMYK 4 + alpha 1）
- manifest：`output.color_mode=cmyk`、`tac_max_pct=300.0`、`tac_mean_pct=129.09`、
  `plate_purity_ok=True`、`generated_pixel_ratio=0.0`、`deterministic_fill_ratio=0.037`

### 第九轮：ICC/TAC 印前合规线（ADR-007，commit 0d536ba）

**🔴 纠正概念错误**：文档与 `profiles/README.md` 原写"TAC 上限从 ICC profile 派生"。
实测 + 标准查证确认这是**错的**：
- ICC 规范（ISO 15076-1）**未定义 TAC/TIL/黑版生成字段**；实测系统 39 个 ICC 的 tag 无任何相关项
- TAC 是**印刷工艺参数**（ISO 12647-2 按纸张/印刷方式规定，或印厂工艺单给定）
- profile 与印刷条件是**配对关系**，不是"profile 里存 TAC"

**🔴 但另一项实测让 ICC 从"可选"变"必需"**：
| 转换方式 | TAC 最大 | K 最大 |
|---|---|---|
| 朴素 `convert('CMYK')` | 276.5% | **0.0%** |
| ICC CoatedFOGRA39 | 328.2% | **97.7%** |

⇒ **朴素转换完全不生成黑版（K=0）**，深色区靠 CMY 三色叠印 → 印刷上灰平衡不稳、小字发虚。
这比 TAC 超标更严重，也是"必须用 ICC 分色"的真正理由。

**实现**：
- 新增 `engine/core/ink_limiter.py`：
  - `PRINT_CONDITIONS` 工艺常量表（每条标出处）：ECI 实践 300%、ISO 12647-2 单张涂布 330%、
    轮转涂布 300%、非涂布 260%(FOGRA47)、GRACoL 300%、新闻纸 240%(Walstead CE)
  - `resolve_policy()`：preset > 印刷条件 > ICC 名称推断 > 保守默认，来源可追溯
  - `limit_ink()`：MaxK 限制 + TAC 压制（**保持 K、等比缩 CMY**以保住中性灰）+ 合规数据快速路径
  - ⚠️ **量化方向坑**：反码 = 255 - 墨量，对反码**截断会放大墨量**（实测 300.0%→300.78%），
    必须对反码**向上取整**
- `color_manager`：`bgr_to_cmyk_raw(bgr, icc_path)` ICC 驱动转换 + transform 缓存
- `psb_builder`：`icc_path` / `tac_policy` 参数，Section5/背景/各层统一压制
- `run_universal_engine`：新增 `--icc`；preset 新增 `icc_path`/`print_condition`
- `profiles/README.md` 重写纠错；提示 Windows 自带 ICC 仅供开发验证

**端到端实测（--icc CoatedFOGRA39，369.0s）**：
- `color_mode=4 (CMYK)`、11 图层、1.74 GB
- 自动推断印刷条件 `eci_coated_practice`；TAC **330.2% → 300.0%**（compliant=True）
- 压制像素 654392（0.52%）、K 限制 205751 px、`plate_purity_ok=True`

**性能取舍（已知，待优化）**：Step6 66.90s → **217.54s**。实测归因（非 transform 构建，
实测其仅 0.14s）：ICC 转换约朴素 2-3 倍 + TAC 浮点压制（3000×1464 单次 0.945s）为主因
+ 输出数据量 +25%（有黑版后熵更高，RLE 压缩率 61.4%→76.8%）。
已做两项优化（transform 缓存 + 合规快速路径）；下一步可做**稀疏压制**（仅对超限的 0.48% 像素运算）。
