## 一、先把事实摆清楚

### 1.1 你的硬件配置（任务管理器截图 + OpenVINO 实测确认）

| 设备 | 规格 | 实测状态 |
| :--- | :--- | :--- |
| CPU | Intel Core Ultra 9 285H，16 核，基准 2.90 GHz | 生产中 25% 占用、1.87 GHz（未跑满频） |
| 内存 | 31.6 GB（双通道） | 占用 12.9 GB / 41% |
| **GPU 0** | Intel Arc 140T，16 GB 共享内存（iGPU） | **实测最快**（LaMa 0.223s） |
| **GPU 1** | NVIDIA RTX 5070 Laptop，**8 GB 显存**（dGPU） | 1% 占用，48°C（基本闲置） |
| NPU 0 | Intel AI Boost | **0%，"无"**（从未被调用） |
| 磁盘 | C:/D: + E: 双 NVMe SSD | 0% |

**这是一台配置均衡的 AI PC 移动工作站，硬件本身没有买错。** 问题出在"用哪块硬件跑什么任务"。

### 1.2 跨设备实测：同一模型谁最快

LaMa ONNX，512×512 输入，各设备编译 + 推理：

| 设备 | 编译 | 推理（最快） | 相对 Arc |
| :--- | ---: | ---: | ---: |
| CPU (Ultra 9) | 12.24s | 1.072s | 4.8× 慢 |
| **GPU.0 (Arc 140T)** | 22.19s | **0.223s** | **基准** |
| GPU.1 (RTX 5070) | 21.26s | 1.222s | **5.5× 慢** |
| NPU (AI Boost) | — | 编译失败 | — |

> **反直觉但可解释**：OpenVINO 对 NVIDIA 只能走 **OpenCL** 后端，对 Intel 走原生 **Level Zero**
> 后端。后者对 Intel 硬件的算子融合与内存布局优化充分，所以 Arc 反而更快。
> ⇒ 项目文档中"RTX 5070 满血冲锋 + Arc 仅作护盾"的架构假设**与实测相反**。

### 1.3 RTX 5070 为什么没被用上（决定性测试）

```
torch 2.6.0+cu124   编译架构仅到 sm_90
RTX 5070 Laptop     算力 sm_120（Blackwell），显存 8 GB
cuda.is_available() True           ← 有误导性，驱动可见 ≠ 能算
2048×2048 矩阵乘    RuntimeError: no kernel image is available for execution on the device
```

**版本限制，不是代码问题。** PyPI 上 torch 2.7.0 ~ 2.14.0 已支持 Blackwell。

## 二、硬件是否浪费？—— 不浪费，但**用途严重错配**

### 2.1 四块硬件的实际分工 vs 设计定位

| 硬件 | 设计文档定位 | **实测实际承担** | 利用率评价 |
| :--- | :--- | :--- | :--- |
| RTX 5070 (8GB) | 主算力（`primary_device`） | 仅 LaMa 补全；且比 Arc 慢 5.5× | **严重闲置** |
| Arc 140T (16GB) | 防爆显存护盾（`shield_device`） | **实际主力**：RealESRGAN 全图 45 切片超分 | **过载主力** |
| NPU | UI 中作为可选设备项 | **零调用**（`grep NPU` 仅命中配置文件） | **完全闲置** |
| CPU | 熔断兜底 | **扛下最贵的 Step 1**：GroundingDINO+SAM2 分割 102.68s（占端到端 35%） | **超负荷** |

### 2.2 关于"驱动本地大模型"的正面回答

**你的机器能跑什么：**

| 模型规模 | 是否可行 | 说明 |
| :--- | :--- | :--- |
| 7B~8B LLM（Q4 量化） | ✅ 可行 | 约 4~5 GB 显存，5070 8GB 够用 |
| 14B LLM（Q4 量化） | 🟡 勉强 | 需 8~10 GB，需部分 offload 到内存，速度下降 |
| 32B 及以上 | ❌ 不可行 | 8 GB 显存是硬限制 |
| Qwen-Image-Layered 20B | ❌ 不可行 | 项目文档自己写明"需 16GB+ VRAM" |
| SDXL / 扩散模型全精度 | ❌ 不可行 | 需 10~12 GB |

**但更关键的问题是：这个项目需要大模型吗？答案是不需要。**

图像分层与印前制版的本质是**几何 + 色彩 + 语义的确定性计算**，不是语言理解或内容生成任务。
项目文档自己也写明 **ADR-010"默认路径不引入生成式扩散大模型"**。

⇒ **"无法驱动本地大模型"这件事，对这个项目不构成损失。**
真正的损失是：**用错了模型类型**（下面详述）。

## 三、技术栈与项目需求的匹配度：我的判断是"错配"，错在三处

### 3.1 错配一：用「开放词汇大模型」做「封闭 5 类」分类 —— 杀鸡用牛刀，且用错了刀

**项目需求原文（ADR-012）**：业务图为**封闭 5 类**（壁布 / 烫金 / 水墨 / 屏风 / 油画），超出转人工。

**当前实现**：GroundingDINO（694 MB）+ SAM 2（156 MB）= **850 MB 模型**，CPU 推理 **102.68 s**。

**致命错配点**：GroundingDINO 的核心价值是**开放词汇**——用任意自然语言 prompt 检测训练时
未见过的类别。但你的业务**只需要固定 5 类**。为了这个用不上的"开放"能力：

- 付出 850 MB 模型体积 + 102s CPU 推理
- 换来**金地假阳性**：prompt `"red stamp . cinnabar seal"` 在金色背景上框出大片区域，
  SAM 2 抠出覆盖 8.77% 画幅的掩模（正确印章仅 0.0119%）——**这正是我上一轮修的 605 倍泄漏**
- 还产生 2.9 GB 的第三方源码依赖（`third_party/`）与 copyleft 合规负担

**实测证据（神经 vs 规则引擎，相对 baseline 的 IoU）**：

| 图层 | 纯规则引擎 | 含神经 | 神经的价值 |
| :--- | ---: | ---: | :--- |
| 07 高士人物 | **0.000** | **0.314** | 显著（规则做不到） |
| 06 水榭草堂 | 0.042 | **0.321** | 显著 |
| 04A 前景峭壁 | 0.162 | **0.250** | 中等 |
| 09B 题跋 | 0.313 | 0.259 | **负贡献** |

⇒ 神经分割对"人物/建筑"这类**规则引擎确实无能为力**的目标有真实价值，
但它不该用 850 MB 的开放词汇模型去实现——**这是可以用 10~50 MB 的专用小模型解决的问题**。

**更合适的方案**：在 5 类图上微调一个轻量语义分割模型（如 U-Net / DeepLabV3-MobileNet /
SegFormer-B0），产出 10~50 MB 权重，
- 推理可在 **NPU** 或 CPU 上跑（NPU 的适用场景恰恰就是这类轻量持续推理）
- 预期 Step 1 从 **102.68s → 数秒级**
- 消除开放词汇模型的金地假阳性
- 顺带解决 `third_party/` 850 MB 依赖与许可问题

### 3.2 错配二：用「生成式超分」填补 4× 分辨率缺口 —— 这是印前的大忌

**这是我认为最需要你正视的一点。**

**事实**：

| 项 | 数值 | 含义 |
| :--- | ---: | :--- |
| 有效源分辨率 | **37.5 PPI** | 原始真实信息量 |
| 交付宣称 | **150 PPI** | 放大 4.0× |
| 频域约束 | 产物中 **~75%** 频率内容超出源图 Nyquist | **物理上不可能是"恢复"，只能是"生成"** |
| RealESRGAN 高频能量 | Lanczos 的 **28.16×** | 大量新增高频结构 |
| RealESRGAN 往返 MAE | **4.782**（Lanczos 仅 1.110） | 降采样回原尺寸后**无法还原源图**，即改变了像素 |

**为什么这在印前是问题**：

1. **违反项目自己的铁律 R1**："禁止人工伪色；生成/补全内容**必须标记为重建区**"。
   当前 Step 5 超分产生的生成像素**占比接近 100%（全画幅）**，却**没有任何标记**；
   而 Step 4 的遮挡补全（仅占 0.31%）反而做了标记。**标记策略与生成规模完全倒挂。**
2. **PLATE 制版线的验收要求**是"可复算、可对色、可过 TAC 审计"。超分生成的高频内容：
   - 不可复算（换超分模型结果就变）
   - 影响色彩（往返 MAE 4.78）
   - 印刷厂拿到的是"AI 想象的 150 PPI"，实物上的纹理不是原作纹理
3. **这直接解释了 MAE 为什么降不到 2.0**：Section 5 用的就是 RealESRGAN 输出，
   它的往返 MAE 本身就是 4.78。**"MAE ≤ 2.0"与"使用生成式超分"在数学上互斥。**

**我的判断**：对于**装饰性远观产品**（壁布、屏风，观看距离 1.5 m+），
37.5 PPI 放大到 150 PPI 是可以接受的工程妥协——但**必须如实披露**，
并在质检单上写明"有效源 37.5 PPI / 生成内容占比"。
对于**精细复刻类产品**（传统书画复刻），这条路走不通，应改为：
**要么提高拍摄分辨率（重拍），要么接受较小的物理输出尺寸。**

### 3.3 错配三：钱花在 DESIGN 线，真正的付费场景 PLATE 线没通

| 产品线 | 目标客户 | 实测状态 |
| :--- | :--- | :--- |
| DESIGN 设计线（RGBA 元素层） | 设计师看图/微调 | 🟡 本轮已修复掩模泄漏，基本可用 |
| **PLATE 制版线（CMYK 分色版）** | **印刷厂（真正付费方）** | 🔴 **未打通**：微孔/烫金/陷印/轮廓/接缝五算子均已实现，
却**无一接入生产链路**；实测产物色彩模式为 **RGB**，不是 CMYK |

⇒ 当前所有算力（分割 102s + 超分 91s + 补全 39s）**服务的都是设计线**。
而印前工作站的核心卖点——CMYK 分色、专色、陷印、微孔刀模——**一个都还没产出**。

## 四、我的专业建议：三条可选路线

### 路线 A：**收敛为「严肃印前工具」**（我最推荐，也最符合项目定位）

> ⚠️ **措辞修正（2026-09-10 晚）**：本节初稿写"超分改诚实模式：默认 Lanczos/边缘导向非生成式"，
> 若读作"**全局**禁用生成式超分"，则会与路线 C 冲突（C 允许 DESIGN 线生成）。
> 正确表述是：**超分策略按产品线隔离**——A 不是与 C 并列的另一条路线，
> 而是 **C 的落地执行**。下表已修正。

| 动作 | 归属 | 理由 |
| :--- | :--- | :--- |
| **打通 PLATE 线**（CMYK/微孔/专色/陷印） | A = C 的执行 | 这是"印前制版工作站"的核心价值，也是付费场景 |
| **超分按线隔离**：PLATE 线强制非生成式（Lanczos/边缘导向）；DESIGN 线可用 RealESRGAN，但必须输出生成区掩码并**随图层持久化** | **= C 的策略在超分环节的落地** | 符合铁律 R1；让印刷厂知道哪些像素可信 |
| **分割替换为 5 类专用小模型** | A 的独立动作 | 102s → 数秒；消除金地假阳性；释放 NPU；摆脱 850 MB 依赖 |
| 输出质检单强制披露：有效源 PPI、放大倍率、生成内容占比 | A = C 的执行 | 达成目标 G3（指标诚实可披露） |

**预期**：端到端从 294s → **60~90s**；产物可用于实际印前交付；NPU 与 5070 都能派上用场（升级 torch 后）。

#### A 与 C 的关系（澄清）

| | 路线 C | 路线 A |
| :--- | :--- | :--- |
| 层次 | **策略层** | **执行层** |
| 回答的问题 | 谁能用生成内容？ | 怎么把这个边界落地？ |
| 产出 | 双产品线的生成边界定义（DESIGN 可生成 / PLATE 禁生成） | 打通 PLATE、超分按线隔离、换轻量分割模型、质检披露 |

⇒ **两者不冲突，是同一件事的策略与执行两面。** A 去掉"按线隔离"这一条后就与 C 冲突，
加上它就是 C 的实现。

#### ⚠️ C 落地时最容易忽略的陷阱：DESIGN 线产物会回灌 PLATE 线

计划 §4 的数据流写明：**「设计师微调 → 回灌制版线」**。这意味着：

若 DESIGN 线使用了生成式超分，其生成细节会**随图层一起回灌进制版链路**，
"C 的隔离"就在回灌处被击穿。

**因此 C 的隔离必须是强隔离，且生成区掩码要随图层持久化**（写入 PSB 图层命名/元数据或 sidecar
manifest），而不能只停留在运行日志里（当前 Step 4 的 `reconstruction_mask` 就只打了日志，
未随产物落盘）。回灌时应能识别并剔除/标记生成内容——这正是 §3.1 硬边界 1
"任何生成式模型的输出不得进入 PLATE 线"的落地要求。

### 路线 B：**强化为「设计师辅助工具」**（把 DESIGN 线做深）

放弃印前严肃性，专注"一键出分层 PSD 给设计师"：
- 继续用生成式超分（设计师看的是效果，不是印刷还原度）
- 补 WebUI（G4）、图层预览、导出 PSD
- 分割精度继续用 AI 模型迭代

**风险**：与"印前制版"定位偏离，可能不是你的真实商业模式。

### 路线 C：**混合**——DESIGN 线走 AI 增强（可生成），PLATE 线走确定性计算（禁生成）

这是计划文档 ADR-011 双产品线的**本意**，也是架构上最正确的设计。
当前问题只是：**PLATE 线没实现，且 DESIGN 线的生成行为没有与 PLATE 线隔离**。

## 五、结论（直接回答你的两个问题）

### Q1：硬件配置浪费了吗？

**硬件没买错，配置是当前 AI PC 的合理选择。但当前技术栈把它用在了错误的地方。**

- Arc 140T 被当"护盾"用，实际它是最快的（实测快 5.5×）；
- RTX 5070 8GB 因 torch 版本限制完全闲置（可修：升级 torch ≥2.7）；
- NPU 从未被调用（因为选的模型太重、太动态，NPU 跑不动）；
- 最重的分割任务压给了 CPU。

**修正调度策略 + 换掉过重的模型，这台机器完全够用，且能快 3~5 倍。**

### Q2：技术栈与项目需求是否合适？

**部分合适，但有三处结构性错配：**

1. 🔴 **开放词汇大模型做封闭 5 类** —— 用不上的能力、付不起的代价（850MB / 102s / 假阳性）
2. 🔴 **生成式超分做印前交付** —— 与铁律 R1 冲突，且生成像素占比近 100% 却零标记
3. 🔴 **PLATE 制版线未打通** —— 算力全花在 DESIGN 线，真正付费的印前能力未产出

**一句话**：这不是"硬件配得太好而用不上"的问题，而是**"用错了模型类型、跑错了产品线"**的问题。
硬件是够的；把分割换成专用小模型、把超分改成诚实模式、把 PLATE 线打通，
这台机器就能真正发挥出来。
