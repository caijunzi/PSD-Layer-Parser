## 一、项目总览

### 1.1 定位与目标

面向**软装壁布、金属烫印面料、传统书画复刻、商业专色网印**的**工业级 2D 智能图像分层与印前制版工作站**，定位为**本地单人 Windows 高性能工作站**（不做云端、不做多用户）。

业务闭环是一条三段式流程：

```
① 拆解（DESIGN 设计线：RGBA 元素层）→ ② 设计师在 PS 中微调/重组/排版 → ③ 制版（PLATE 制版线：CMYK 分色版）
```

业务图为**封闭 5 类**（壁布 / 烫金 / 水墨 / 屏风 / 油画），超出范围转人工（ADR-012）。

### 1.2 双产品线（ADR-011）

## 三、核心实现说明

### 3.1 生产主链路（`run_universal_engine.py`，6 步）

```
Step1 语义分割   GroundedSAMProvider → 失败/未命中则回落 ZeroHardcodeSegmentationProvider
Step2 底板重构   UniversalBackgroundExtractor（LaMa 神经补全 / 扇面拼接）
Step3 层序排序   UniversalLayerSorter（语义 Z 序 + 接触图拓扑）
Step4 遮挡补全   DeocclusionOperator（Telea 旁路 + LaMa）
Step5 超分       RealESRGANProvider 全图 + guided_upsample_mask 逐层（6 线程）
Step6 组装写盘   UniversalPSBBuilder + codecs_accelerator（C-SIMD PackBits）
```

### 3.2 关键实现机制（均已实测确认）

1. **中文图层名修复**：`pytoshop.nested_layers_to_psd` 内部 `reversed(layers)` 导致层序翻转，`psb_builder.py:135` 用 `zip(recs, reversed(layers_to_build))` 对齐 luni 标签 — **实测图层名与顺序均正确**。
2. **C-SIMD 写盘**：`codecs_accelerator.install_psb_codec_accelerator()` 替换 `pytoshop.codecs.packbits` / `compress_rle` / `compressors[rle]`。
3. **双分支降级**：GroundingDINO/SAM2 未加载时自动回落规则引擎，主包零重依赖设计成立。
4. **分辨率注入**：`struct.pack('>IHH IHH')` 写入 0x03ED 块，**实测 150.0 × 150.0 PPI 正确**。

### 3.4 🔴 致命缺陷：元素掩模质量相对旧基线大幅退化

把当前产物与它自己取代的旧基线 `masks_16k/`（v2.1 手工调优成果）逐层对比：

| 图层         |           旧基线 `masks_16k/` 填充率 |                **当前产物填充率** | 判定                       |
| :--------- | -----------------------------: | -------------------------: | :----------------------- |
| `09A` 朱红印章 | **0.0145%**（BBox 仅 310×259 px） | **8.775%**（BBox 7604×7608） | 🔴 **泄漏 605 倍**，印章层覆盖整幅画 |

| `09B` 题跋墨书 |                        0.0652% |                     2.745% | 🔴 泄漏 42 倍               |
| `05A` 前景枯木 |                        2.5083% |                    15.205% | 🔴 泄漏 6 倍                |
| `10A` 外框绫边 |                     **11.16%** |                 **0.014%** | 🔴 **近乎空层**（RK-11 类缺陷重现） |

**结论**：文档宣称的"11 个图层全部具备动态紧凑最小包围盒、彻底告别全屏黑底（RK-10 已关闭）"**与物理事实不符**——11 层中有 6 层的 BBox 覆盖全画幅的 40%~76%，设计师在 Photoshop 中拖动"印章"会拖走半幅画。**M6 的核心验收标准（设计师可拖动单个元素）实际未达成。**

根因定位：`ZeroHardcodeSegmentationProvider` 的规则分割把"大块墨色区域"当成语义对象，再由 `_map_to_bilingual_names()` 的 27 条硬编码映射**在命名层面伪装成语义层**。名称是语义的，掩模不是。

### 5.2 质检体系有效性（重点）

`tests/audit_system_integrity.py` 五个维度全部"100% 通过"，但**它没能发现印章层泄漏 605 倍**。逐条拆解：

| 维度        | 问题                                                                                              |
| :-------- | :---------------------------------------------------------------------------------------------- |
| D1 硬件探活   | `assert "GPU.1" in devices` / `assert "NPU" in devices` — **硬绑本机硬件**，换机即 100% 失败，不是回归测试，是本机点名   |
| D2 零硬编码   | 只扫 **8 条历史黑名单正则**（如 `[2700, 920]` 这些早已删除的旧常量）。**永远不可能发现新魔法值**，形同自证清白                            |
| D3 交付物合规  | `assert len(psd) in [11, 15]` — **事后追认窗口**，不校验任何掩模质量                                            |
| D4 防伪代码   | 只查 4 条正则（`pass` / `return None # mock` / `time.sleep(...) # simulate`），且主动排除 `base_provider.py` |
| D5 C-SIMD | 只断言"属性替换成功"，**未验证写盘时真的走了 C 路径**（无开关对比）                                                          |

**实际仍存在的硬编码**（D2 扫不出来）：

| 位置                                | 内容                                                                                      |

### 5.3 性能与内存隐患

| #  | 隐患                                                                                                           | 影响                                                                                                                         |

### 7.1 P0-1 掩模泄漏：根因重定位并修复 ✅

**关键发现：泄漏不在分割阶段，而在「神经掩模无条件覆盖」。**

三步递进定位（每步以实测排除假设）：

| 步骤 | 方法 | 结果 | 结论 |
| :--- | :--- | :--- | :--- |
| 1 | 新建 `tests/diagnose_mask_quality.py`，以 `masks_16k` 为 golden baseline | 规则引擎在 LR 下印章层 0.0119%、IoU 0.700，**正常** | 泄漏不在分割阶段 |
| 2 | 检验产物层 alpha 分布 | **硬二值双峰**（>200 占 18.79%，中间灰度仅 0.19%），与源图亮度相关性 ≈0 | 排除引导滤波连续泄漏 |
| 3 | 直接运行 `GroundedSAMProvider` | 神经输出与产物填充率**精确吻合**（印章 8.7745% vs 产物 8.775%） | **锁定根因** |

**根因（两条）**：

1. `grounded_sam_provider.segment_objects` 中 `final_masks[k] = m` **无条件覆盖**规则掩模。
   Grounding DINO 在**金地背景**上对 `"red stamp . cinnabar seal"` 产生假阳性大框
   （诱因：`box_threshold=0.25` 过低、单框面积上限 30% 过松），SAM 2 在该框内抠出大片金地，
   把规则引擎算出的正确印章掩模（0.0119%，BBox 68×63）静默抹除。
2. ROI 检测 `|profile - median(profile)| > 5.0` 失效：本图外框灰度 88、画心 183，
   而行中位数 160 偏向画心，导致几乎所有行都"偏离中位数"，ROI 被判为整幅画，
   `~roi_mask` 恒空 → 外框层退化为空层。

**修复方案**：

- `grounded_sam_provider`：新增**神经掩模质量门**（按语义类别的面积预算 + 相对规则掩模的放大倍数
  + 形状 IoU 三重校验），未通过者保留规则掩模并显式告警；`box_threshold` 0.25→0.35，
  单框面积上限 30%→8%。
- `segmentation_provider`：新增 `_detect_painting_roi`，以「边缘带 / 中心区双参考 + 连续 run 判定」
  替代中位数偏差法。

**修复效果（诊断实测）**：

| :--- | ---: | ---: | ---: | ---: |

| 08 芦雁 | 6.6332% | **0.1744%** | 0.0651% | 0.124 |

3. **总耗时 294.6s vs 文档 168s**：差异主要来自 Step 1（CPU 神经推理 102.68s）

   掩模正确性应由 `audit_system_integrity.py`（相对基线）与 `verify_r6_composition.py` 承担。

## 八、三个本地模型的实效实测（2026-09-10 晚）

> 问题："本地 3 个模型到底起作用了吗？"——**加载成功与跑完不等于起作用**，以下均为对照实测。

### 8.1 GroundingDINO + SAM 2 — ✅ 生效，且有显著正贡献

对比「纯规则引擎」与「最终（含神经、经质量门）」相对 `masks_16k` 基线的 IoU：

| 图层 | 规则引擎 IoU | 含神经 IoU | 变化 |
| :--- | ---: | ---: | :--- |
| 07 高士人物 | **0.000**（完全失败） | **0.314** | 从零救回 |
| 06 水榭草堂 | 0.042 | **0.321** | **+664%** |
| 04A 前景峭壁 | 0.162 | **0.250** | +54% |
| 09B 题跋 | 0.313 | 0.259 | 略降 |
| 08 芦雁 / 09A 印章 | — | 被质量门拒绝，保留规则结果 | 判定正确 |

⇒ 神经分割解决了规则引擎**根本做不到**的语义识别（人物、建筑）。质量门拒绝了 2 个金地假阳性，
避免重新引入 605 倍泄漏。**模型有效，但必须配质量门**——这正是 §7.1 事故的教训。

### 8.2 RealESRGAN — ✅ 生效，增益显著

768×768 → 3072×3072 对照（`scratch/probe_esrgan.py`）：

| 指标 | Lanczos4 | RealESRGAN | 倍率 |
| :--- | ---: | ---: | ---: |
| 高频能量（Laplacian 方差） | 10.8 | **303.0** | **28.16×** |
| 往返 MAE（超分→降回 vs 源） | 1.110 | 4.782 | 4.31× |
| 神经输出 vs Lanczos 平均绝对差 | — | 6.357 | — |
| 耗时 | 0.059s | 6.052s | 102× |

⇒ 锐度提升 28 倍，与 Lanczos **非等价**。**这同时解释了 MAE 为何降不到 2.0**：
Section 5 用的就是 RealESRGAN 输出，其本身就会偏离源图（往返 MAE 4.78）。
**MAE ≤ 2.0 与"使用 RealESRGAN"在数学上互斥**——这是目标之间的内在冲突，需要重新定标。

### 8.3 LaMa — ⚠️ 修复前在部分 ROI 形状下完全失效，已修复

**根因**：`_inpaint_tiled` 的切片起算 `range(0, max(1, h - 512), 448)` 在 ROI 任一维度 < 512 时
返回 `[0]`，切片 `[0:512]` 被 Python 截断，产生 396×512 / 512×396 这类非 512 tile，继而：

1. batch stack 后与 OpenVINO LaMa 固定输入 `[?,3,512,512]` 不符 → **整批熔断回退 Telea**；
2. 回退后回填 `out_acc[0:512,…] += tile(396,512,3) * hann(512,512,1)` → **广播失败抛 ValueError**。
   生产中该异常被 `deocclusion_operator` 外层 `try/except` 兜底成 Telea，因此未暴露，
   但**LaMa 在所有这类 ROI 形状下实际从未生效**。

**实测对照**（`scratch/probe_lama.py`）：

| ROI 形状 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| 396×696（高<512） | 熔断 + ValueError，0.61s（Telea） | **无熔断，4.58s（LaMa 真推理）** |
| 696×396（宽<512） | 熔断 + ValueError，0.45s | **无熔断，2.07s** |
| 696×696 / 796×796 / 996×1196 | 正常 | 正常 |

**修复**：新增 `_tile_starts()`（保证切片完整落在范围内）与 `_pad_to_tile()`（不足 512 的 tile
用 `BORDER_REFLECT` 补齐、掩模常量 0 补齐，推理后按实际尺寸裁回），并以 th/tw 实际尺寸
记账、同步裁剪 Hann 窗。commit `9e3507e`。

> **探针踩坑**：首版探针用圆形小洞（900 px），触发 `inpaint()` 的「微孔 <2500 px 快速旁路」
> 直接返回 Telea，导致全部场景"无熔断"的**假阴性**；改用矩形洞才能精确控制 ROI 形状
> （ROI = 洞 bbox + 2×48 px pad）。**教训：探针输入必须落在被测分支内。**

## 十、硬件配置实效实测（2026-09-10 晚）

> 问题："我的硬件配置在调用这些模型时到底起作用了吗？"
> —— 结论：**硬件本身没问题，但实际分工与文档宣称的架构定位严重不符。**

### 10.1 设备清单（OpenVINO 实测可见）

| 设备 ID | 型号 | 类型 |
| :--- | :--- | :--- |
| `CPU` | Intel Core Ultra 9 285H | 16 核 |
| `GPU.0` | Intel Arc 140T GPU (16GB) | iGPU（共享内存） |
| `GPU.1` | NVIDIA GeForce RTX 5070 Laptop (8GB) | dGPU |
| `NPU` | Intel AI Boost | NPU |

### 10.2 同一模型的跨设备实测（LaMa ONNX，512×512 输入）

| 设备 | 编译耗时 | 推理耗时（最快） | 状态 |
| :--- | ---: | ---: | :--- |
| CPU | 12.24s | 1.072s | ✅ |
| **GPU.0（Arc 140T）** | 22.19s | **0.223s** | ✅ **最快** |
| GPU.1（RTX 5070） | 21.26s | 1.222s | ✅ 可用但慢 |
| NPU（AI Boost） | — | — | ❌ **编译失败**（LaMa 动态 shape 不支持） |

> **关键反直觉结论**：在同一 OpenVINO 路径下，**Arc 140T 比 RTX 5070 快 5.5 倍**
> （0.223s vs 1.222s）。原因是 OpenVINO 对 NVIDIA 走 **OpenCL** 后端、
> 对 Intel 走原生 **Level Zero** 后端，后者优化充分。
> ⇒ 文档中"RTX 5070 满血冲锋 + Arc 仅作护盾"的架构假设**在本项目技术栈下不成立**。

### 10.3 PyTorch 对 RTX 5070 的可用性（决定性测试）

```
torch 版本            : 2.6.0+cu124
torch 编译支持的架构  : ['sm_50','sm_60','sm_61','sm_70','sm_75','sm_80','sm_86','sm_90']
可见 CUDA 设备        : [0] NVIDIA GeForce RTX 5070 Laptop GPU  算力 sm_120  显存 8.0 GB
cuda.is_available()   : True          ← 有误导性
2048x2048 矩阵乘 GPU  : ❌ RuntimeError: CUDA error: no kernel image is available for execution on the device
```

⇒ **RTX 5070 无法被 PyTorch 使用**（sm_120 不在 torch 2.6.0+cu124 的编译架构内）。
这**不是代码偷懒，而是 torch 版本限制**——`grounded_sam_provider.py:125/128/270` 中
`device="cpu"` 的写死，客观上只能如此。

### 10.4 各硬件在本次生产运行中的实际分工

| 硬件 | 文档定位 | **实际承担** | 证据 |
| :--- | :--- | :--- | :--- |
| RTX 5070 (GPU.1) | 主算力（`primary_device`） | **仅 LaMa 补全一处**；且实测比 Arc 慢 5.5× | `probe_hardware`；`inpainting_provider` 默认 GPU.1 |
| Arc 140T (GPU.0) | 防爆显存护盾（`shield_device`） | **实际主力**：RealESRGAN 全图超分（45 切片） | `realesrgan_provider.py:119-124` 主动从 5070 切至 GPU.0 |
| NPU (AI Boost) | `device_config.py` 中作为 UI 可选项 | **零使用**，且实测模型编译失败 | `grep NPU engine/` 仅命中配置文件 |
| CPU (Ultra 9) | 熔断兜底 | **承担最重的一步**：GroundingDINO + SAM2 语义分割 102.68s（占端到端 35%） | 生产日志 Step 1 耗时 |

### 10.5 结论与可选改进路径

**硬件配置起作用了吗？** —— 起了，但**不是按设计文档设想的方式起的**：

1. **名义主算力 5070 实际是最弱的一环**（在 OpenVINO 路径下）；
2. **名义"护盾"的 Arc 140T 实际承担了主要计算**（超分 + 在 LaMa 上也更快）；
3. **NPU 是纸面设备**，只在 UI 下拉框里存在，从未被调用（且现有模型跑不动）；
4. **CPU 扛下了最昂贵的分割任务**，这是端到端 294.6s 中最大的一块。

**可选的改进路径**（按投入产出排序）：

| # | 路径 | 预期收益 | 成本/风险 |
| :-- | :--- | :--- | :--- |
| A | **升级 torch 至 ≥2.7.0 + cu128**（PyPI 现有 2.7.0~2.14.0），使 SAM2/GroundingDINO 真正上 5070 | Step 1 从 102.68s 大幅下降，端到端有望回到 180s 量级 | 需重装 torch（约 2-3 GB）、验证 SAM2/GroundingDINO 与新 torch 的兼容性 |
| B | **把 SAM2/GroundingDINO 转 OpenVINO IR**（与 LaMa 同样路径） | 可同时用上 Arc 与 5070，避开 torch 兼容问题 | 动态 shape（SAM2 的 prompt、DINO 的文本编码器）转换复杂，工作量大 |
| C | **设备策略改为实测选优**：把 LaMa 默认设备由 GPU.1 改为 GPU.0 | 补全推理 1.222s → 0.223s（5.5×） | 需同步修正 profile 语义（当前 `primary_device=GPU.1` 与实测最优相悖） |
| D | 为 NPU 选择适配模型（如轻量检测算子） | 释放 NPU | 收益有限，优先级最低 |

> **架构认知修正**：`profile_config.py` 中"RTX 5070 满血冲锋 + Arc 16GB 护盾"的定位，
> 与 OpenVINO 在本机上的实测性能分布**相反**。若继续沿用该假设做调度决策，
> 会持续把最重的算子派给最慢的设备。

## 十一、一句话结论

**这是一个工程思考深度远超平均水平、但"文档完成度"显著高于"物理完成度"的项目**：性能工程（8.74× 提速）与 PSB 底层（中文层名、C-SIMD 写盘、150 PPI）确实扎实落地并经验证；但**元素分层这一核心业务价值发生了相对旧基线的大幅退化，而现有质检体系因为断言设计无效而对此完全失明**。建议按 P0 顺序先止血（回归掩模质量 + 建 git + 修文档数值 + 重写审计），再按 P1 完成内核合流与 PLATE 线打通。
